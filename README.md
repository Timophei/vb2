# vb2 — бот-консультант по сценарию состояний

PHP 8.3 + SQLite + OpenAI. Вторая версия визового бота: вместо одного большого промта — **движок, который исполняет сценарий** (JSON): состояния, слоты, переходы, действия в Битрикс24, таймеры. Сценарий загружается и правится в админке, версии хранятся.

Ставится на тот же сервер, что v1 (Ubuntu 24.04, nginx, PHP 8.3-FPM), отдельным поддоменом `vb2.b-integration.ru`, в `/var/www/vb2`. С v1 ничего общего: своя папка, своя база, свой Telegram-бот.

## Как устроен ход

```
сообщение клиента
  → событие client_message            (closed → greeting, postponed → возврат)
  → КЛАССИФИКАТОР (модель, строгий JSON): intent + слоты из реплики
  → движок: слоты записаны → переходы (сначала global_transitions, потом состояния),
            цепочкой: jobs → jobs_finish → closed; при переходе on_exit / on_enter / таймеры
  → ОТВЕТЧИК (модель): промт собирается из global_prompt_rules + goal/instruction/forbidden
            состояния + известные/недостающие слоты + каталог + база знаний разделов состояния;
            инструменты — только из "tools" состояния (счёт, анкета, биометрия)
  → события от инструментов (invoice_sent) → снова переходы
```

**Переходы решает код, а не модель.** Модель только разбирает реплику и пишет текст. Поэтому бот не может «выставить счёт из визы», а в карточке диалога видно, почему он оказался в этом состоянии.

**Сумму счёта считает код** по каталогу: (наша цена тарифа, а если её нет — товара + опции) × участники. Пустая цена — бот говорит «уточнит менеджер» и счёт не выставляет. «Плата банку» — справочно, в счёт не входит.

**Каталог** правится в админке или загружается из Excel (Каталог → Excel; образец — `scenarios/cards_catalog_draft.xlsx`): листы «Продукты», «Тарифы», «Характеристики», «Опции», «Вопросы». Ячейки с «?» в начале — пометки, бот их не видит. Вопросы раздела (например, `cards`) становятся полями `q.<раздел>.<код>` и попадают в промпт состояний с `knowledge: catalog:<раздел>` — сценарий править не нужно. Это **подсказки, а не анкета**: бот выводит ответы из разговора, спрашивает только самое нужное (колонка «Важный: да» — без ответа рекомендация может оказаться неверной) и держится между `min_questions_before_offer` и `max_questions_before_offer` вопросов до рекомендации. Если на паузе часть товаров раздела, бот подбирает из остальных; если клиент называет паузный — объявление один раз.

**Заметки** (Материалы → Новая заметка) — текст в базе знаний, который можно править прямо в админке.

**Счёт в тестовом режиме:** у счёта порядковый номер (№ 0001…), бот присылает QR-код (qrencode) со ссылкой на демо-страницу оплаты. Сканируете телефоном → «Оплатить (демо)» или «Ошибка оплаты» → бот сам продолжает диалог.

## Выгрузка для анализа

Настройки → «Выгрузка для анализа (Битрикс24)», только для администратора. Берёт данные **портала**, а не бота: все диалоги открытых линий всех сотрудников и CRM за период. Только чтение.

- **Диалоги (zip):** `dialogs.jsonl` (сессия = строка: линия, канал, ответственный, лид/сделка/контакт, реплики с временем и типом автора client/manager/bot/system), `dialogs.txt`, `messages.csv`.
- **CRM (xlsx):** лиды созданные и закрытые, сделки созданные, закрытые и выросшие из лидов периода, контакты, звонки, сводка по диалогам. Связи: контакт и дата его создания, сделки из лида, «лид из другого периода», флаги «повторный».
- Персональные данные маскируются по умолчанию (телефон `7914***4567`, почта `iv***v@mail.ru`, фамилия до буквы, карта — 4 последние цифры).
- Период — до 6 месяцев. Сбор идёт фоновым процессом (`bin/b24export.php`, запускает админка) с паузой 250 мс между запросами и пакетами по 10 историй, ход и журнал шагов видны в админке, есть «Отменить». Готовый файл лежит в `data/exports` до скачивания (не дольше 3 часов) и удаляется после скачивания. Вебхук — `b24_export_webhook` (права crm, imopenlines, user), иначе `bitrix_webhook`. Кнопка «Проверить доступ» показывает права и пробную сессию.
- Диалоги ищутся через дела CRM открытых линий (`IMOPENLINES_SESSION`): сессии без связи с CRM не попадают.

### Выгрузка из базы Битрикса (рекомендуется)

Читает MySQL портала напрямую (только SELECT) через SSH-туннель, который открывается на время выгрузки и сразу закрывается. Пароль MySQL не хранится — вводится в админке при каждом запуске и передаётся процессу выгрузки только через окружение. SSH-ключ лежит в `data/ssh` и на стороне Битрикса умеет только пробросить порт MySQL.

1. **Сервер бота:** `sudo apt install php8.3-mysql && sudo systemctl restart php8.3-fpm`; в `config.php` — блок `b24_db` (см. `config.example.php`); админка → Настройки → Выгрузка → «Подключение к базе» → «Создать SSH-ключ», скопировать строку.
2. **Сервер Битрикса — пользователь для туннеля:**
   ```bash
   sudo useradd -m -s /usr/sbin/nologin vb2tunnel
   sudo install -d -m 700 -o vb2tunnel -g vb2tunnel /home/vb2tunnel/.ssh
   sudo nano /home/vb2tunnel/.ssh/authorized_keys      # вставить строку из админки целиком
   sudo chown vb2tunnel: /home/vb2tunnel/.ssh/authorized_keys && sudo chmod 600 /home/vb2tunnel/.ssh/authorized_keys
   ```
   Если в `/etc/ssh/sshd_config` есть `AllowUsers` / `AllowGroups` — добавить vb2tunnel; `AllowTcpForwarding` не должен быть `no`.
3. **Сервер Битрикса — пользователь MySQL** (имя базы — в `/home/bitrix/www/bitrix/.settings.php`, обычно `sitemanager`):
   ```sql
   CREATE USER 'vb2_read'@'127.0.0.1' IDENTIFIED BY 'длинный-пароль';
   CREATE USER 'vb2_read'@'localhost' IDENTIFIED BY 'длинный-пароль';
   GRANT SELECT (ID, NAME, LAST_NAME, EXTERNAL_AUTH_ID) ON sitemanager.b_user TO 'vb2_read'@'127.0.0.1', 'vb2_read'@'localhost';
   ```
   и SELECT на нужные таблицы (только существующие в этой версии):
   ```bash
   sudo mysql -N sitemanager <<'SQL' | sudo mysql
   SELECT CONCAT('GRANT SELECT ON `', TABLE_SCHEMA, '`.`', TABLE_NAME, '` TO ''vb2_read''@''127.0.0.1'', ''vb2_read''@''localhost'';')
   FROM information_schema.TABLES WHERE TABLE_SCHEMA = DATABASE() AND TABLE_NAME IN (
    'b_crm_lead','b_crm_deal','b_crm_contact','b_crm_status','b_crm_field_multi','b_crm_utm','b_crm_deal_category','b_crm_item_category',
    'b_uts_crm_lead','b_uts_crm_deal','b_uts_crm_contact','b_user_field','b_user_field_lang','b_user_field_enum',
    'b_imopenlines_session','b_imopenlines_config','b_im_message','b_im_message_param','b_crm_act','b_crm_act_bind','b_crm_act_comm');
   SQL
   ```
   MySQL должен слушать `127.0.0.1:3306` (`ss -ltn | grep 3306`).
4. **Админка:** «Проверить подключение к базе» с паролем — туннель, права, таблицы, пробная сессия.

Каждый запрос ограничен 60 с (MAX_EXECUTION_TIME / max_statement_time), сессия MySQL — только чтение. Сессии открытых линий берутся все (и без CRM), в `dialogs.jsonl` у каждой есть поле `session` — время первого ответа, `worktime` по настройкам линии и т. п.

## Установка

```bash
# 1. Пакеты (если ещё нет после v1)
sudo apt install -y git poppler-utils qrencode fonts-dejavu-core php8.3-sqlite3 php8.3-curl php8.3-mbstring php8.3-zip php8.3-xml php8.3-gd

# 2. Код
sudo git clone https://github.com/Timophei/vb2.git /var/www/vb2
cd /var/www/vb2
sudo cp config.example.php config.php
sudo nano config.php        # ключ OpenAI, токен Telegram, вебхук Битрикс24, public_url

# 3. Права
sudo mkdir -p data && sudo chown -R www-data:www-data data && sudo chmod 770 data
sudo chown root:www-data config.php && sudo chmod 640 config.php

# 4. nginx + HTTPS
sudo cp deploy/nginx-vb2.conf /etc/nginx/sites-available/vb2
sudo ln -s /etc/nginx/sites-available/vb2 /etc/nginx/sites-enabled/
sudo nginx -t && sudo systemctl reload nginx
sudo certbot --nginx -d vb2.b-integration.ru

# 5. Воркер таймеров (напоминания, ожидание оплаты, «отложено»)
sudo cp deploy/vb2-worker.service /etc/systemd/system/
sudo systemctl daemon-reload && sudo systemctl enable --now vb2-worker

# 6. Telegram-вебхук (новый бот от @BotFather; токен и secret — из config.php)
curl "https://api.telegram.org/bot<ТОКЕН>/setWebhook" \
  -d "url=https://vb2.b-integration.ru/telegram.php" \
  -d "secret_token=<telegram_secret>"

# 7. Проверка всего сразу
sudo -u www-data php bin/check.php
```

Откройте `https://vb2.b-integration.ru/admin/` — при первом входе админка предложит создать администратора.

## Обновление

```bash
sudo bash /var/www/vb2/deploy/update.sh
```

`config.php` и `data/` (база, файлы) в git не хранятся и при обновлении не трогаются. Сценарий и каталог живут в базе — правки из админки не теряются.

## Админка

- **Песочница** — чат «как клиент» + справа всё о диалоге: состояние, слоты (обязательные подсвечены), таймеры, переходы, действия, что ушло в модель. Кнопки: событие (оплата прошла / не прошла / менеджер взял…), «прошло N минут» (таймеры), перейти в состояние, записать слот, сброс. В Битрикс24 песочница **не пишет** — в журнале видно, что ушло бы (можно включить кнопкой, если `bitrix_mode = live`).
- **Диалоги** — все диалоги с фильтром по состоянию и каналу; карточка такая же, как в песочнице, плюс ответ от имени менеджера (бот встаёт на паузу по правилу сценария).
- **Сценарий** — схема состояний, список незаполненного (TODO), редактор JSON с проверкой, загрузка файла, версии. Каждый диалог помнит свою версию; в карточке его можно перевести на активную.
- **Каталог** — карточки товаров: варианты (тарифы) с ценами и сроками, опции с надбавками, «цена за заказ / за участника», кто продаёт (бот или менеджер), текст для бота, параметры (период регистрации DV, акция).
- **Материалы** — база знаний **по разделам**: `general`, `visa/general`, `visa/<страна>`, `cards`, `green_card`, `jobs`. Состояние ищет только в своих разделах (`knowledge` в сценарии). Таблица показывает, какие разделы сценарий ждёт и какие пусты.
- **Настройки** — приветствие, кнопки-подсказки, состояние системы и **справочник Битрикс24**: права вебхука, стадии лидов, воронки и стадии смарт-процесса — чтобы вписать коды в `settings.hr` сценария.

## Битрикс24

Входящий вебхук (права **crm**; для будущих открытых линий — ещё imbot, imopenlines, im) → `bitrix_webhook` в config.php.

- `bitrix_mode => 'dry'` (по умолчанию) — ничего не отправляется, в журнале действий видно, что ушло бы. Начинайте с него.
- `bitrix_mode => 'live'` — пишет по-настоящему: для диалогов с сайта и из Telegram бот создаёт лид при первой записи в CRM.

Поля в действиях сценария со значением `TODO…` пропускаются с пометкой в журнале — сценарий можно запускать недозаполненным. Слоты без своего поля Б24 пишутся текстом в «Комментарий» лида, отдельным блоком `=== Бот vb2 ===`, который обновляется на месте и не трогает заметки менеджеров.

**HR-воронка** (состояния `jobs` → `jobs_finish`): вакансия → название лида, ФИО → поля имени, контакт → телефон/e-mail, резюме → таймлайн лида, элемент смарт-процесса 1038 со связью с лидом, лид → стадия `UC_IGWO64` (последней — чтобы при ошибке лид не ушёл в провал пустым). Ошибка в любом шаге → диалог уходит менеджеру.

**Сделки и контакты** (вкладка «Битрикс24» → «Направления»): для визы, карт, Green Card можно вести не лид, а **контакт + сделку**. Сделка создаётся, когда понятен продукт и известен контакт клиента (или дошли до счёта / передачи менеджеру). Контакт сначала ищется по телефону и e-mail среди существующих (найденный не правится), иначе создаётся. Для каждого направления: воронка, стадия при создании, стадии по этапам бота (например «Ожидание оплаты» → «Заключение договора и оплата»), значение поля «Услуга», ответственный. Сумма счёта → сумма сделки.

**Поля** сопоставляются отдельно для лида, сделки и контакта с существующими полями портала. Списки заполняются по совпадению текста (классификатор получает варианты списка и называет значение точно); нет в списке — «Другой / Другая», исходное значение — в комментарий. Там же — проверка **обязательных полей** и значения по умолчанию для тех, что бот не заполняет.

С портала данные читаются только по кнопке «Загрузить с портала».

Открытые линии подключим после теста в веб-чате.

## Сценарий: справка по JSON

- `states.<имя>.type`: `conversation` (разговор), `transit` (пишет одно сообщение и сразу дальше), `waiting` (ждём события), `terminal` (закрыто). После `terminal` новый круг начинается с чистыми слотами (контакты остаются: `settings.keep_slots_on_restart`) и новым лидом.
- Условия переходов (`on`): `slot`+`eq`, `slot_set`, `slot_not`, `slots_complete: "required"`, `any: [...]`, `intent`, `event` (+`count_gte`), `counter`+`gte`, `always`. Несколько ключей — «И».
- Переход в то же состояние не повторяет `on_enter` (не дублирует уведомления).
- Шаблоны: `{{slot}}`, `{{jobs.full_name.last}}`, `{{settings.hr.lead_status_id}}`, `{{lead.id}}`, `{{x | default: 'текст'}}`.
- Действия: `say` (`text` — готовый текст; `from: instruction` — пишет модель по инструкции этого состояния), `b24_update_lead` (`fields`: объект или `"slots:visa.*"` / `"slots:all"`), `b24_attach_resume`, `b24_create_smart_item`, `openline_finish`, `notify_manager`. У действия может быть `if` (условие). У состояния — `on_error`.
- Таймеры: `after_minutes` или `at_slot`, `start_on: "bot_answered_question"` (перезапуск после каждого ответа), `condition`, `max_fires`, `action: {say | event}`.
- Интенты: `intents.list`; описания для классификатора можно задать в `intents.descriptions`.

## Стиль ответа и профиль клиента

- `settings.reply_style` — лимиты ответа: `max_sentences`, `max_chars`, `max_questions` (за сообщение), `min_questions_before_offer` / `max_questions_before_offer` (уточнений до рекомендации в этапах с подбором: раньше min рекомендовать нельзя — кроме торопливого клиента по профилю, после max — пора), `overflow_allowed_for` (когда можно длиннее), `format` — правила оформления (абзацы, списки «- », вопрос последним абзацем; пусто — оформление по умолчанию). Подставляются в промпт вместо «1–4 абзаца». Пост-проверка: ответ длиннее `max_chars × shorten_factor` (с суммами и сроками — `× shorten_factor_terms`) или с лишними вопросами перегенерируется один раз с просьбой сократить, цены и условия сохраняются; ответы после счёта и анкеты не трогаются. В журнале действий — `reply_shorten`.
- Слот типа `object` с `fields` — **скрытый профиль клиента** (в сценарии `client.profile`: приоритет цены, уровень сервиса, стиль решения). Классификатор на каждом ходе возвращает для полей `value / confidence / evidence`; `unknown` ничего не меняет, новый сигнал пересматривает оценку. Ответчик получает профиль отдельным блоком «предположения, не факты». В Битрикс, уведомления менеджеру и «что известно» скрытые слоты (`hidden: true` или тип `object`) не попадают; в карточке диалога видны.
- Счётчики в карточке: `asked_before_offer.<этап>` — уточняющих вопросов до рекомендации, `offered.<этап>` — бот уже назвал товар.

## Прогон тестовых диалогов (с моделью)

```bash
sudo -u www-data php bin/simulate.php --list               # персонажи
sudo -u www-data php bin/simulate.php                      # все по разу
sudo -u www-data php bin/simulate.php --persona=premium,budget --runs=3 --scenario=12
```

Модель играет клиента с заданным характером (торопливый премиум, экономный, обстоятельный, «не знаю, что хочу», срочный, Green Card, виза), бот отвечает настоящим движком в песочнице (в Битрикс не пишет). Итог — `data/sim/<дата>/report.txt` (длина ответов, вопросы до рекомендации, на каком ответе названа карта и выставлен счёт) и стенограммы. `--scenario=<id>` — версия из админки, не обязательно активная. Стоит денег OpenAI: ~10 ходов × 2–3 запроса на диалог.

## Оценка качества диалогов другой моделью

```bash
sudo -u www-data php bin/judge.php --dialogs=27,29,30     # ручные тесты из песочницы
sudo -u www-data php bin/judge.php --last=5               # последние 5 диалогов песочницы
```

Модель-оценщик (`judge_model` в config.php, лучше сильнее, чем у бота) читает стенограмму, правила сценария и каталог и ставит баллы 1–5 по критериям `settings.quality_rubric` (вежливость, слышит клиента, квалификация, рекомендация, точность, краткость, оформление, чистота; 0 — неприменим), плюс худшую реплику и советы, что поправить в инструкциях. Оценка пишется в журнал действий диалога (`judge`) и в `data/judge/`. `bin/simulate.php` оценивает каждый прогон сам (`--no-judge` — выключить) и считает средние баллы по критериям — видно, где бот слабее всего.

## Важное

- Бот собирает персональные данные (имя, телефон, резюме). По 152-ФЗ нужна политика обработки ПД: ссылка в `privacy_url`, она появится под чатом.
- Бэкап — копия папки `data/` (база `vb2.sqlite`, загруженные файлы).
- Файлы от клиентов (резюме) — до `max_upload_mb` (15 МБ), лежат в `data/uploads/`.
